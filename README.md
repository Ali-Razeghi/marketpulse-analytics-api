# MarketPulse Analytics API

A **multi-source data integration and analytics platform** built with FastAPI.
It ingests financial time-series from heterogeneous sources:  a crypto API, an
FX-rate API, and a deterministic synthetic generator normalises them into a
single store, and serves analytics (summary statistics, moving averages,
cross-series correlation) over a documented, authenticated REST API. Uploaded
CSV files are profiled in memory as a separate one-time data-quality workflow.

## Architecture

```mermaid
flowchart TD
    subgraph Sources["Data sources (pluggable)"]
        C[Crypto / CoinGecko]
        F[Forex / Frankfurter]
        S[Synthetic / offline]
        U[User CSV upload]
    end
    C & F & S --> N[Normalize -> NormalizedPoint]
    U --> P[Pandas profiling]
    N --> R[(PostgreSQL: data_points)]
    R --> A[Analytics service]
    A --> API[FastAPI + JWT auth]
    P --> API
    API --> D[Swagger / ReDoc / clients]
```

The codebase follows a strict **layered architecture**. A request flows:

```
API route  ->  Service (business logic)  ->  Repository (data access)  ->  DB
                     |
                     +-- Source adapter (external data)  -> NormalizedPoint
```

Each layer has one responsibility, which keeps the code testable and makes the
system open for extension (new sources) without modification of existing code.

## Features

- **Authentication** registration, login, JWT bearer tokens, `bcrypt`
  password hashing.
- **Role-based access control (foundation)**: a `user` / `pro` / `admin` role
  model with admin-only routes (`/admin/users`, role changes) guarded by an
  authorization dependency. Extending RBAC to more routes is on the roadmap.
- **Pluggable data sources** a single generic `DataSource[P]` contract with
  a typed, validated parameter model per source; adding a provider is one new
  ~40-line class plus a one-line registry entry.
- **Unified time-series store** every value from every source becomes a
  `(source, series_key, ts, value, unit, meta)` row, so one analytics engine
  serves all of them.
- **Idempotent ingestion** re-ingesting a series replaces its stored points
  (backed by a unique constraint on `(source, series_key, ts)`), so analytics
  are never skewed by duplicates.
- **Analytics** descriptive summary, rolling moving average, and Pearson
  correlation between two aligned series (via pandas).
- **CSV profiling** upload a CSV and receive a structural + statistical
  profile. *Profiling is one-time; the file/profile are not yet persisted
  (see Limitations).*
- **Standardised errors** every failure returns
  `{"error": {"code", "message", "details"}}`.
- **Quality gates** `ruff` (lint + format), `mypy --strict`, `pytest`, all
  enforced in CI.
- **Containerised** `docker compose up` starts the API and PostgreSQL with
  migrations applied automatically.

## Quickstart

### Option A: Docker (recommended)

```bash
cp .env.example .env
# Generate and place a strong SECRET_KEY in .env, for example:
# openssl rand -hex 32
docker compose up --build
```

Docker Compose intentionally refuses to start when `SECRET_KEY` is missing.

API: <http://localhost:8000>  ·  Swagger: <http://localhost:8000/docs>

### Option B Local (SQLite)

```bash
python -m venv .venv && source .venv/bin/activate
pip install ".[dev]"
alembic upgrade head
uvicorn app.main:app --reload
```

## Example usage

Register and log in:

```bash
curl -X POST localhost:8000/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"me@example.com","password":"supersecret1"}'

TOKEN=$(curl -s -X POST localhost:8000/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"me@example.com","password":"supersecret1"}' | jq -r .access_token)
```

Ingest a series, then analyse it:

```bash
# Offline synthetic source (no API key, always works):
curl -X POST localhost:8000/api/v1/ingest/synthetic \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"series_key":"demo/index","days":30}'

# Real crypto data:
curl -X POST localhost:8000/api/v1/ingest/crypto \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"coin_id":"bitcoin","vs_currency":"usd","days":30}'

curl -G localhost:8000/api/v1/analytics/summary \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "source=crypto" --data-urlencode "series_key=bitcoin/usd"
```

Example summary response:

```json
{
  "source": "crypto",
  "series_key": "bitcoin/usd",
  "count": 31,
  "first_value": 61000.0,
  "last_value": 67250.5,
  "min_value": 59800.0,
  "max_value": 68100.0,
  "mean_value": 64120.7,
  "std_value": 2140.3,
  "pct_change": 10.25
}
```

## Project structure

```
app/
  core/         config, security (JWT/bcrypt), error envelope
  db/           async engine, session, declarative base
  models/       SQLAlchemy ORM models (User, DataPoint)
  schemas/      Pydantic request/response contracts
  repositories/ data-access layer (no business logic)
  sources/      DataSource abstraction + typed params + adapters + registry
  services/     business logic (auth, ingestion, analytics, csv)
  api/v1/       HTTP routes (auth, users, admin, ingestion, analytics, datasets)
tests/          pytest suite (mocked HTTP, in-memory DB)
alembic/        migrations
docs/images/    screenshots used in this README
scripts/mockups/ scripts that generate the (illustrative) images
```

## Testing

```bash
pytest -q                       # run the suite
ruff check app tests              # lint
ruff format --check app tests     # formatting gate
mypy app                          # strict type check
```

Tests are fully **offline and deterministic**: external HTTP is mocked with
`respx` and the database is in-memory SQLite, so no API keys or running services
are required.

## Extending: add a new data source

1. Create `app/sources/<name>.py` with a class subclassing `HttpDataSource`
   (or `DataSource`) that implements `collect(...) -> list[NormalizedPoint]`.
2. Register it in `app/sources/registry.py` (`build_sources`).
3. Add a test in `tests/test_sources.py`.

No other layer changes. This is the whole point of the abstraction.

## Project status

Portfolio project / MVP built to demonstrate backend engineering. It is **not**
intended for production use or for making real financial decisions.

## Current limitations (honest scope)

- **CSV profiles are not persisted.** Upload returns a profile but stores
  nothing; the returned `dataset_id` is not retrievable later. Dataset
  persistence + `GET/DELETE /datasets` is planned.
- **CSV data does not enter the time-series store yet.** External sources do;
  importing CSV columns as personal series is a planned extension.
- **RBAC is a foundation, not comprehensive.** Admin routes exist and are
  guarded, but most routes are not yet role-differentiated.
- **No refresh tokens.** Only short-lived access tokens are issued.
- **No rate limiting or caching** (Redis-based rate limiting is planned).
- **Analytics run in pandas (in memory).** Fine for the demo's data sizes; for
  large series, aggregation should be pushed into SQL.
- **All ingested market data is global.** Per-user/private data ownership is
  designed for (the `user_id` column and access model) but only relevant once
  private sources exist.

## Roadmap

- Persist datasets: `POST/GET/DELETE /datasets`, profiles stored in PostgreSQL
- Import CSV columns as user-owned time series (private data ownership)
- Refresh tokens + role-based access control across more routes
- Scheduled ingestion worker (APScheduler / Celery + Redis)
- Redis caching and per-user rate limiting
- Push heavy aggregation into SQL for large series
- Real dashboard (Streamlit or React) consuming the API

## Security notes

- Secrets are provided only via environment variables; `.env` is git-ignored.
- Passwords are bcrypt-hashed; login errors are generic to avoid user
  enumeration.
- Per-source parameters are validated with Pydantic before any network call.
- CORS is disabled by default and must be explicitly configured for a frontend.
- Docker Compose requires an explicit `SECRET_KEY`; no production fallback is used.
- The container runs as a non-root user.
